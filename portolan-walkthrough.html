Registry→ Catalog→ Dataset→ Query→ Answer

The agent doesn’t know the datasets in advance. It discovers them — the way you’d explore a set of tools.

The skill teaches the agent to:

  • Find data — across a federation of catalogs
  • Describe data — read each dataset’s own metadata
  • Write queries — compose its own SQL
  • Use engines — DuckDB, Snowflake, BigQuery…
  • Provide feedback — back to the publisher

It doesn’t hard-code anything — it learns to operate on this framework.

📍 A spatial query on the registry itself

Before attaching anything, the agent filters the catalogs by their bbox against the site — so it only opens the ones whose extent actually covers Espoo.

-- keep only catalogs covering the site
WHERE bbox_intersects(child.bbox,
        ST_Point(24.65, 60.20))

Eurostat / Overture / Fingrid are skipped for this question — relevance + location, decided up front.

Attach the catalogs

The agent ATTACHes the catalogs like they were databases

INSTALL iceberg; LOAD iceberg; LOAD spatial;
ATTACH 'nls' (TYPE iceberg,
  ENDPOINT '…/national-land-survey',
  AUTHORIZATION_TYPE 'none');  -- no login

SELECT id, properties.semantics, schema
FROM nls.catalog.datasets;

Anonymous, no portal, no login — each catalog mounts like a database.

Inside: every dataset describes itself

Each carries an OSI — Open Semantic Interchange block (what it means + unit), its CRS, and its schema:

  • sahkolinja → “distance to electricity transmission lines”
  • tulvasuojtoistuvuus = flood return period (yr)
  • vaesto = inhabitants per 1 km cell
  • class_2018 = Urban Atlas land-use class
  • geom_wkb = geometry → transform to EPSG:3067 for metres

The agent reads this metadata to write the right query — nothing is hard-coded.

● LIVE  DuckDB querying 4 catalogs at the same time

One SQL query · four sovereign publishers · joined live

Each catalog became a database — and the agent joins them in a single query, live, across publishers and countries.

WITH site AS (SELECT ST_Transform(ST_Point(24.65,60.20),'EPSG:4326','EPSG:3067') g)
SELECT
  (SELECT min(ST_Distance(geom,s.g)) FROM nls.v2.power_lines)    AS power_m,      -- 🇫🇮 NLS (national)
  (SELECT min(ST_Distance(geom,s.g)) FROM syke.v2.flood_hazard)  AS flood_m,      -- 🇫🇮 SYKE (national)
  (SELECT class_2018 FROM cop.v2.urbanatlas
        WHERE ST_Contains(geom,s.g))                      AS land_use,     -- 🇪🇺 Copernicus (EU)
  (SELECT sum(vaesto) FROM statfi.v2.statfi_popgrid
        WHERE ST_DWithin(geom,s.g,5000))                  AS people_5km   -- 📊 Statistics FI
FROM site s;

The real defect the agent found

  • Fingrid · electricity_consumption (+ Eurostat sibling)
  • A non-spatial table is tagged bbox:[-180,-90,180,90] — a whole-world extent
  • Contradicts the registry (bbox:null, geospatial:false) and makes a table with no geometry falsely match every location in bbox pre-filtering
  • Fix: set bbox: null + guard generate_stac.py to emit null geometry

A fix to data went through the same review + CI as a code change — guarded by the catalog’s own validation gate. The contribution loop closes.

No server, no API to run

This way of publishing is serverless for everybody

The same static files on object storage are read four ways — by a human, an engine, a standard client, or a direct download. Nobody runs a server.

① Human — a web page

The catalog’s own index.html explorer opens in any browser. HTTP 200 ✓

…/repo/portolan-statfi-catalog/index.html

② Engine — one line of SQL

ATTACH 'c'(TYPE iceberg, ENDPOINT '…/portolan-statfi-catalog',
  AUTHORIZATION_TYPE 'none');
SELECT count(*) FROM c.v2.statfi_popgrid;  -- 1,188

③ Standards — STAC + OGC API

…/catalog.json (STAC) and …/records/catalog.json (OGC API - Records). both 200 ✓

④ Direct — download the files

The Parquet/Iceberg objects are just files on object storage — fetch them, or read with Snowflake, GDAL, anything. No server.

“ATTACH, iceberg_scan, STAC/Records, direct download — and a human web page. One open artifact, no server, sovereign by where it’s hosted.”

Serverless economics

Cost that doesn’t scale with popularity

No server in the request path — so cost is dominated by storage, not by how many people hit the data. Scenario: a 50 GB open dataset goes viral — 5 TB/month downloaded, 500 concurrent users.

Traditional WFS / GIS servers

  • Fleet of ~10–20 instances + load balancer + spatial DB to absorb the concurrency
  • Egress billed per GB; continuous ops — patching, autoscaling, monitoring
  • ≈ €2,000–4,500 / month — and it climbs with every spike

Portolan — static on object storage

  • Storage: 50 GB × ~€0.01/GB ≈ €0.50 / month
  • Object store absorbs any concurrency; egress free / near-free on modern stores
  • ≈ €1–50 / month — essentially flat as it grows

Server cost scales with concurrency; object-storage cost is dominated by storage — the more popular the data, the bigger the win, often 10–100×.

And onboarding is often zero-cost: data already in cloud-native formats — Cloud-Optimized GeoTIFF, GeoParquet — that already sits behind a cloud-storage service is used as-is. The catalog points at the existing files in place; nothing is re-created or copied.

Rough, illustrative order-of-magnitude figures.

What makes it all work

The magic is in cloud-native formats

Cloud-native formats let an engine query and access data directly on object storage — reading only the bytes it needs, no download, no import, no server. That’s what makes every data type below work the same way.

📐 Vector ● live in this demo
Points · lines · polygons. GeoParquet + Apache Iceberg tables (WKB geometry, bbox-pruned).
🛰️ Raster ● live in this demo
Imagery · DEM · indices. COG (Cloud-Optimized GeoTIFF) + raquet (raster-in-Parquet, queried in SQL).
🟢 Point clouds
LiDAR · 3D scans. COPC (Cloud-Optimized Point Cloud) + PDAL pipelines.
🚗 Mobility data
Trajectories · flows · origin-destination. GeoParquet + mobility extensions, same columnar files.

This demo ships vector (Iceberg) and raster (raquet); point clouds and mobility are the same files-on-storage pattern — nothing about the architecture changes.

Nothing proprietary, nothing exotic

No new standards — applying standards to existing technology

Portolan invents nothing. It composes battle-tested technology the whole industry already runs — and the more a piece is maintained outside the geospatial community, the better: bigger ecosystem, longer life, less to maintain ourselves.

🧊 Apache Iceberg
Open table format — backed by Snowflake, BigQuery, Databricks, AWS, Trino, Spark.
🗂️ Apache Parquet
The columnar standard — read by virtually every data tool on earth.
🛰️ STAC
The de-facto open standard for describing & discovering spatial assets.
🌐 GeoParquet · OGC API
OGC standards for vector-on-Parquet and Records — interop by spec, not by glue.
🔧 Git
Universal version control & collaboration — the contribution loop runs on it.
🪣 S3 API
Object storage available from every cloud — and self-hostable (MinIO, Ceph).

Every layer is a standard with a huge ecosystem. Portolan is composition, not invention — that’s why it’s durable and sovereign.

Portolan (open spec) + CARTO for Publishers (commercial)

The spec stays open — CARTO for Publishers is the commercial layer.

Everything you saw is open files, open formats, open engine — anyone can run it. Portolan is the open specification + tools. For publishers that need governance, monetization and enterprise integration, CARTO for Publishers is the commercial product on the same open foundation:
