The agent does not know the datasets in advance. It discovers them — the way you’d explore a set of tools.

Four asks, one point

  • Land use — what’s on the ground
  • Environmental constraints — flood, protected, groundwater
  • Proximity to power — distance to the grid

The hard requirement — “cite the publisher and exact query” — is what an SDI built for provenance can actually deliver.

Step 1 — the skill is loaded

① The sdi skill triggers — a generic discovery loop

It carries no hard-coded datasets. Everything specific — endpoints, schemas, how to query each source — lives in the catalogs’ own metadata. The skill stays generic, so it works as the federation grows from 9 sources to many.

registry → pick a catalog catalog → browse datasets dataset → read schema + semantics compose SQL yourself synthesize an artifact

Why “discover”, not “configure”

  • Adding a publisher = one new link in the registry — no skill code changes
  • Each dataset is self-describing: STAC index + OSI semantics + CRS + schema
  • The agent reads metadata at each step and writes its own queries
  • Runs on open files + an open engine (Iceberg/STAC on EU object storage, DuckDB)

Step 5 — understand each dataset (schema + semantics)

⑤ Read the schema so the query uses the right columns

DESCRIBE SELECT * FROM syke.v2.flood_hazard;
-- id, tulvasuojtoistuvuus (return period, yr),
--     area_m2, perimeter_m, geom_wkb (WKB, CRS84)

DESCRIBE SELECT * FROM statfi.v2.statfi_popgrid;
-- grd_id, vaesto (population), ika_0_14 / 15_64 / 65_,
--     kunta, geom_wkb (1 km cell)

The agent now knows the vocabulary

  • tulvasuojtoistuvuus = flood return period in years
  • vaesto = inhabitants per 1 km cell
  • pvalueluokka = groundwater protection class
  • class_2018 = Urban Atlas land-use class
  • geom_wkb = geometry, WGS84 → transform to EPSG:3067 for metres
Step 6 — compose the query (the agent writes its own SQL)

⑥ One query, four publishers — joined by location

WITH pt AS (SELECT ST_Transform(
   ST_Point(24.65,60.20),'EPSG:4326','EPSG:3067') g)
SELECT
 min(ST_Distance(geom_3067, pt.g)) -- per layer
FROM nls.v2.power_lines, pt;          -- ⚡ power
-- + nls.v2.protected, syke.v2.natura2000,
--   syke.v2.groundwater, syke.v2.flood_hazard …

✓ Real PR — opened & CI passed

PR #1 · jatorre/portolan-fingrid-catalog
github.com/jatorre/portolan-fingrid-catalog/pull/1

validate workflow → 25 checks, 0 problems ✅

The real defect the agent found

  • Fingrid · electricity_consumption (+ Eurostat sibling)
  • A non-spatial table is tagged bbox:[-180,-90,180,90] — a whole-world extent
  • Contradicts the registry (bbox:null, geospatial:false) and makes a table with no geometry falsely match every location in bbox pre-filtering
  • Fix: set bbox: null + guard generate_stac.py to emit null geometry

A fix to data went through the same review + CI as a code change — guarded by the catalog’s own validation gate. The contribution loop closes.

Why this matters — the Portolan idea

SDIs as open, self-describing, agent-usable infrastructure

  • Sovereign — open files on European object storage, queried by an open engine. No GIS server, no portal, no data copies.
  • Federated — 9 independent publishers, joined by location. Adding one = a single new link in the registry.
  • Agent-ready — catalogs describe themselves (STAC + OSI semantics + schema). The agent discovers; it isn’t pre-wired.
  • Provenant — every number keeps its publisher and a re-runnable query. Nothing is a black box.
  • Composable — most real questions need 2–3 publishers; geometry is just a column to join on.
  • Honest — screening, not permitting; claims framed to what the data can actually support.

Registry → catalog → dataset → query → cited answer. The same five steps, at any scale.
